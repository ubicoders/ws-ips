Where ips_image_relay sits.

Each box is its own Rust crate, its own process, its own tmux window. The highlighted box is this folder. A box only talks to the next box through a message, never through code.

Where things live

  • yamlsb.flow.yaml lists the four live modules, the four camera ids and the wires, once. ips_calib runs only in calib.flow.yaml and ips_image_relay only in relay.flow.yaml, so sb up starts neither.
  • yamlEvery module has its own parameters/*.yaml. It is the only place settings come from.
  • protomessages/custom/*.proto defines the two custom messages. Each crate compiles what it uses at build time; the relay compiles the stock ros2 sensor_msgs/Image from the sb vault.
  • genswarmbotix_io/ inside each module is generated by sb. Never edit it.

One run, in order

  • 1sb up builds, then starts cameras, detectors, tracker, viewer. sb up relay starts the same plus the four image relays.
  • 2Once per camera placement: detectors on AprilTag, run ips_calib, restart tracker.
  • 3Detectors back on ArUco. Open rerun to watch.
ips_image_relay · 6 source files · ~1000 lines

Halve the pictures. Put them on the network.x4, optional

The camera picture and the detector's overlay live in iceoryx2 shared memory, which a program on another computer cannot read. The relay takes the newest of both pictures of its camera, shrinks each to half width and half height, and sends it over zenoh under the same topic name. Nothing upstream or downstream changes. It is optional: plain sb up never starts it, sb up relay does.

Files

src/main.rsReads the yaml, opens one zenoh session, starts one thread per camera, runs the loop above over both streams and prints the Hz line.
src/source.rsOne iceoryx2 stream of one camera. Waits for the service to exist, then lends out the newest sample as a borrowed view and drops it straight after.
src/relay.rsOne stream, sample to message: the every skip, the resize while the sample is held, then a reused sensor_msgs/Image filled for sending.
src/scale.rsChecks width, height, step and data_len against the buffer before touching a pixel. Wraps the pixels in a Mat and runs resize with INTER_AREA.
src/rate.rsCounts relayed frames per stream for the Hz line.
src/lib.rs build.rsGlue plus protobuf generation of the stock ros2 sensor_msgs/Image and its std_msgs/Header import, from the sb vault in ~/.swarmbotix/messages/.
swarmbotix_io/subscribers/generatedimage and debug_image, iceoryx2, zero copy. Their default keys are this module's own; source.rs points them at the sources.
swarmbotix_io/publishers/generatedimage and debug_image, zenoh, each sample tagged application/protobuf;ros2/sensor_msgs/Image.
sb.module.yamlThe manifest: two iceoryx2 subscribers in, two zenoh publishers out. sb up relay opens one tmux window per camera, each running the binary with --id sbNN. Plain sb up does not.

Reads

  • iox2.../ips_detect-sbNN/iox2/debug_image as Image1280x1024Color, rgb8, only while ips_detect runs with debug: true
  • yamlparameters/relay_params.yaml: cameras, scale, every
  • cli--id sbNN, the only argument

Writes

  • zenoh.../ips_image_relay-sbNN/zenoh/image as sensor_msgs/Image, 640x512 mono8
  • zenoh.../ips_image_relay-sbNN/zenoh/debug_image as sensor_msgs/Image, 640x512 rgb8
  • stdouta waiting line per missing source every 5 s, then one Hz line per camera every 5 s. No files.

Optional, so it lives in its own flow. relay.flow.yaml is the whole pipeline plus the four relays: sb up relay, or sb down && sb up relay when a session is already up. Only with that flow active do sb run ips_image_relay and sb stop ips_image_relay work.

Beside the default flow, start it by hand from this folder: target/release/ips_image_relay [--id sbNN]. Without --id it is one process with one thread per camera in relay_params.yaml.

Nothing else changed. ips_detect, ips_track and ips_viz still read the full-size iceoryx2 pictures; the relay is one more reader of the same streams.

Only the module segment and the transport differ from the source key; the topic stays image or debug_image. To get every camera, subscribe with the sub-segment wildcard ips_image_relay-$*, as ips_track does for markers.

debug_image exists only while ips_detect runs with debug: true. Without it the relay keeps printing its waiting line, reports debug_image 0.0 Hz, and relays image alone.

The stamp is the camera's capture time, the same one ips_detect puts on its markers, so a peer can pair a picture with its detections.

Do not detect or calibrate on the relayed picture. The lens numbers in sbNN-camchain.yaml belong to the full 1280x1024 frame.

iceoryx2 0.9.3 hands Ctrl-C to only one node. That thread sets a shared STOP flag, and the other camera threads check it every loop.

words that keep showing up

Seven words, plain.

iceoryx2
A mailbox in shared memory. Two programs on the same computer pass a big picture by pointing at it instead of copying it.
zenoh
A post office for small messages. Programs publish to a named key; anyone subscribed to that key gets a copy, even over the network.
protobuf
The packing format for a message. The .proto file is the packing list; each crate generates Rust structs from it at build time.
intrinsics
The lens numbers of one camera: focal length, image centre, distortion. From Kalibr, in camchain.yaml.
extrinsics
Where a camera sits in the room and which way it points: a rotation R and a shift t. Made by ips_calib.
Kabsch fit
Given two lists of matching 3D points, find the one rotation and shift that lay one list on top of the other with the least error. Used twice: for cameras, then for cubes.
rerun
A 3D log viewer. Programs send it points, boxes, images and numbers over time; it draws them with a timeline.
