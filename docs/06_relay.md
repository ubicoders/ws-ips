# 06 Image relay

Full at handout, nothing to fill. The camera frames and the detectors' annotated frames live in iceoryx2 shared memory, which only processes on the host can open, so a network peer such as the Flutter app cannot read them. `ips_image_relay`, one per camera like the detectors, subscribes to both image streams of its camera, halves them (1280x1024 to 640x512, OpenCV `INTER_AREA`), and republishes them over zenoh under the same topic names: `<device>/ws_ips/ips_image_relay-sbNN/zenoh/image` (`mono8`) and `.../ips_image_relay-sbNN/zenoh/debug_image` (`rgb8`), both protobuf `sensor_msgs/Image`. The header stamp, `frame_id` and encoding are copied from the source frame, so a peer can match an image to its markers and to the cube pose of the same stamp. `ips_detect`, `ips_track` and `ips_viz` are unchanged and keep reading the full-resolution streams.

The relay is optional and not part of `sb up`: it is a node of the relay flow only, `relay.flow.yaml`, the live pipeline plus one relay per camera. `sb down && sb up relay` (plain `sb up relay` when no session runs) starts everything with the relays, `ips_image_relay-sb00` to `-sb03`; then `sb run ips_image_relay:sb00` restarts one, `sb stop ips_image_relay` closes them while the pipeline keeps running, and `sb down && sb up` returns to the pipeline without them. While the default flow is active, `sb run ips_image_relay` is refused (`module ips_image_relay is not a node of flow default`); beside it, start the relay by hand from `modules/ips_image_relay/` once it is built: `target/release/ips_image_relay` relays every camera in one process, one thread each, and `target/release/ips_image_relay --id sb00` relays one.

A relay waits for each of its two sources on its own and prints a waiting line until it appears. The debug stream exists only while the detectors run with `debug: true` in `modules/ips_detect/parameters/detector_params.yaml`, so it may never come; the camera image is relayed regardless. Every 5 s each relay prints the rate of both streams.

Then from a second machine on the LAN: `sb topic list` shows the relay keys with their rates, and `sb topic listen /<device>/ws_ips/ips_image_relay-sb00/zenoh/image -n 1` decodes one image (the publisher tags it `application/protobuf;ros2/sensor_msgs/Image`). A mono frame is 327680 bytes, so at the cameras' 90 Hz the four mono streams together are about 118 MB/s before zenoh framing, too much for most Wi-Fi links. For a Wi-Fi peer, raise `every` in `modules/ips_image_relay/parameters/relay_params.yaml` (relay every Nth frame per stream) or `scale` (an integer divisor that must divide 1280 and 1024).

Check: `sb topic list` shows `ips_image_relay-sbNN/zenoh/image` for every camera at the camera's rate divided by `every`, and the decoded image is 640x512, `mono8`, step 640, with 327680 bytes of data and the stamp of its camera frame.
